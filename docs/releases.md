# Версии и релизы

## Номер версии `vX.Y.Z`

Правила задал владелец проекта; они **отличаются от обычного semver** (новые функции не повышают среднюю цифру).

| Цифра | Когда повышается | Примеры |
|---|---|---|
| **X** — мажор | Только сверхкрупные, масштабные переработки всей панели | Новая архитектура, несовместимый формат данных, переписанная панель |
| **Y** | Исправление **критических** уязвимостей и багов, которые приводили к утечкам данных или критическим сбоям работы панели | Обход авторизации, утечка секретов/ключей, потеря клиентов или VPN у всех пользователей, падение панели |
| **Z** | Всё остальное: обычные баги, потенциальные уязвимости, доработки и новые функции, не приводившие к серьёзным сбоям | Исправление интерфейса, новая настройка, ужесточение проверок, улучшение установщика |

При повышении цифры младшие обнуляются (`v0.3.7` → `v0.4.0`). Если в одном релизе есть и критическое исправление, и
доработки, номер выбирается по самому серьёзному изменению. Номер только растёт.

## Где хранится версия

- **Единственный источник** — поле `version` корневого `package.json` (без `v`). Сервер читает его при запуске
  (`services/version.service.ts`, `PANEL_VERSION`). `server/package.json` и `client/package.json` версию панели не задают.
- `CHANGELOG.md`: первый раздел `## vX.Y.Z — ГГГГ-ММ-ДД` — текущая версия, ниже — предыдущие по убыванию. Текст раздела
  становится описанием релиза на GitHub. Согласованность проверяет `test/version.test.ts`.

## Как выпустить версию

1. Повысить `version` в корневом `package.json` по правилам выше.
2. Добавить в начало `CHANGELOG.md` раздел `## vX.Y.Z — дата` с описанием изменений для администратора панели (что
   исправлено/добавлено, нужно ли что-то сделать после обновления).
3. Закоммитить вместе с изменениями и запушить в `main`.
4. После зелёного CI workflow `.github/workflows/release.yml` (скрипт `.github/scripts/release.sh`) создаёт тег `vX.Y.Z`
   и релиз GitHub с текстом из `CHANGELOG.md`. Если тег уже есть — ничего не делает; если версия меньше последнего
   релиза или нет раздела в `CHANGELOG.md` — падает.

Правки без изменения поведения (документация, тесты, CI) версию не меняют и релиз не создают. Изменения, которые
копятся в `main` без повышения версии, попадут в следующий релиз — не забывайте записывать их в `CHANGELOG.md`
(раздел следующей версии можно завести заранее, повысив версию в том же коммите).

## Проверка обновлений в панели

`GET /api/version` → `VersionService.getInfo`: текущая версия и последний релиз
`https://api.github.com/repos/ghostoftheeleven/dementia-panel/releases/latest`.

- Ответ кэшируется на 6 ч, после ошибки — повтор через 30 мин; `?refresh=1` (клик по версии в шапке) — не чаще раза в минуту.
- Ответ GitHub — внешние данные: принимается только тег `vX.Y.Z` и ссылка на страницу релиза этого репозитория.
- `DEMENTIA_UPDATE_CHECK=0` в `server/.env` отключает обращения к GitHub.
- В шапке интерфейса (`PanelVersion.tsx`): текущая версия, «актуальная (GitHub: vX.Y.Z)» или ссылка «Доступна vX.Y.Z».
- Панель не обновляется сама: обновление запускает администратор — кнопкой в интерфейсе или повторным запуском `install.sh` (README).

## Обновление из интерфейса

Значок «Доступна vX.Y.Z» в шапке открывает окно обновления (`PanelUpdateModal.tsx`): «Обновить до vX.Y.Z» → подтверждение →
ход обновления и журнал. API: `GET /api/version/update` (можно ли обновить, состояние, журнал), `POST /api/version/update`
`{version}` — только до последнего релиза, который видит панель (`VersionService`), и только вперёд.

Как устроено (`services/update.service.ts`, `scripts/update-panel.sh`):

1. Панель копирует `update-panel.sh` в `data/update/` (git и сборка заменяют файлы панели) и запускает его через
   `systemd-run --unit=dementia-update --collect` — отдельной службой: `install.sh` останавливает `dementia.service`, и
   дочерний процесс службы был бы убит вместе с ней.
2. Скрипт скачивает тег релиза (`git fetch origin refs/tags/vX.Y.Z`) и запускает **`install.sh` из этого релиза** без терминала с
   `PANEL_UPDATE_REF=vX.Y.Z`: вместо `git pull origin main` установщик делает `git merge --ff-only` тега. Дальше — обычное
   обновление: резервная копия БД в `data/backups/`, `npm ci`, сборка, перезапуск, проверка `/api/health`. Логин, пароль, порт,
   `server/.env`, данные и сертификат не меняются; ноды и VPN пользователей работают независимо от панели.
3. Если `install.sh` не удался **после** смены кода — откат: `git reset --hard` на прежний коммит, БД из резервной копии этого
   обновления (новая версия могла изменить схему), сборка и запуск. Если код не менялся (не скачался релиз) — проверяется, что
   служба запущена.
4. Состояние — `data/update/status.json` (`running` → `success` / `rolled_back` / `failed`), журнал — `data/update/update.log`.
   Панель разбирает файл состояния строго; «идущее» дольше 45 минут обновление считается прерванным.

Обновление из интерфейса доступно, только если панель установлена `install.sh`: Linux, служба systemd от root (`INVOCATION_ID`),
каталог панели — клон git с `install.sh`, есть `systemd-run`. Иначе окно объясняет причину и показывает команду для терминала.
`DEMENTIA_SELF_UPDATE=0` в `server/.env` отключает обновление из интерфейса, `DEMENTIA_UPDATE_CHECK=0` — вместе с проверкой.

**Совместимость:** скрипт обновления берётся из *установленной* версии, а `install.sh` — из *новой*. Поэтому `install.sh` обязан
продолжать поддерживать `PANEL_UPDATE_REF` и работу без терминала (инвариант 34 в AGENTS.md). Проверки: `test/panel-update.test.ts`
(API), `test/update-panel-script.test.ts` (скрипт на настоящем git; на Windows — `TEST_BASH=<bash Git for Windows>`),
`test/install/upgrade.sh` U6 (настоящий `install.sh`, успешное обновление и откат несобираемого релиза).
