# Партнёрский доступ к нодам

Две панели делятся нодами: **владелец** выдаёт токен, **получатель** создаёт на нодах владельца клиентов для своих
пользователей. Владелец видит этих клиентов и может их блокировать.

Код: владелец — `services/partner.service.ts`, `routes/partners.ts` (админ), `routes/federation.ts` (публичный API);
получатель — `services/federation-client.service.ts`, `routes/remote-panels.ts`; UI — `PartnersView.tsx`.

## Ключевые решения

- **Приватные ключи клиентов не покидают панель получателя.** Владельцу передаётся только публичный ключ;
  PSK и IP выдаёт владелец.
- **Источник истины о клиентах — панель получателя.** Пиры у владельца, не известные получателю, удаляются при
  синхронизации (так обрабатываются любые удаления у получателя без отдельных уведомлений).
- **Ноды партнёра у получателя — обычные строки `servers`** с `remote_panel_id`/`remote_node_id`, `ssh_user='partner'`,
  `managed_by='partner'`. Поэтому они автоматически работают в выборе нод пользователей, подписках, именах/порядке.
  Все SSH-операции для них запрещены (`loadLocalServer`, `getLocalServerOr404`).
- Только HTTPS (`req.secure`); для разработки `ALLOW_INSECURE_FEDERATION=1` на обеих сторонах.

## Строка подключения

`https://<адрес-панели-владельца>#dp_<43 символа base64url>`. Адрес — `settings.public_url` или адрес, с которого
админ открыл панель. Токен во фрагменте URL. В БД владельца — только `token_hash` (SHA-256) и `token_hint`;
у получателя — токен зашифрован (`encryptSecret`).

## Публичный API владельца `/api/federation/v1`

Авторизация: `Authorization: Bearer dp_…`. Ограничения: 300 запросов/мин на партнёра, 20 неверных токенов за 15 мин
с IP → 429. Отключённый доступ → 403 (получатель помечает панель `revoked`).

| Метод | Путь | Тело / ответ |
|---|---|---|
| GET | `/info` | `{api_version, partner_name, limits}` |
| GET | `/nodes` | `{nodes: [{id, name, host, port, public_key, status, params}], limits}` — `params` как `AwgParams` |
| GET | `/peers` | `{peers: [{id, node_id, name, remote_ref, public_key, client_ip, preshared_key, enabled, owner_blocked, total_rx, total_tx, last_handshake}]}` |
| POST | `/peers` | `{node_id, public_key, name, remote_ref?, enabled?}` → `{peer, node}`. Повтор с тем же `remote_ref` возвращает существующего клиента (идемпотентно). Проверки: нода доступна и установлена, партнёр не приостановлен, лимит клиентов, уникальность ключа |
| PATCH | `/peers/:id` | `{enabled?, name?}` — `owner_blocked` партнёр снять не может: `enabled` сохраняется как его желание, но заблокированный владельцем клиент остаётся выключенным на ноде (`owner_blocked` в ответе), пока блокировку не снимет владелец |
| DELETE | `/peers/:id` | Удаление клиента |

`limits = {max_clients, traffic_limit, expire_at, suspended, usage: {clients, upload, download, used}}`.
Все действия партнёра пишутся в `partner_audit`.

## Активность клиента партнёра на ноде владельца

Клиент попадает в конфиг ноды, только если `owner_blocked = 0`, `partners.enabled = 1`, `partners.suspended = 0` и
нода всё ещё в `partner_nodes` (SQL в `ProvisionService.getServerClients`). Приостановка по сроку/трафику —
`PartnerService.refreshSuspension` (в `statsLoop`). Владелец **не может удалить** клиента партнёра (409) — только
заблокировать: удалённого клиента получатель создал бы заново.

## Синхронизация на стороне получателя (`FederationClient.doSync`, каждые 60 с и по запросу)

1. `GET /nodes` → upsert серверов (имя, адрес, порт, ключ, параметры, статус). Ноды, которых больше нет, получают
   `status = uninstalled` (пропадают из подписок, клиенты сохраняются).
2. Для клиентов без `remote_peer_id` — `POST /peers` с `remote_ref = id клиента`; ответ заполняет `remote_peer_id`,
   `client_ip`, `preshared_key`. Ошибка (например, лимит) → `remote_state = 'error: …'`, повтор в следующий раз.
3. `GET /peers`: обновление трафика (абсолютные значения владельца), `last_handshake`, `remote_state = 'blocked'`;
   выравнивание `enabled` (желаемое = клиент включён и подписчик активен) и имени (переименование клиента или пользователя
   у получателя) через `PATCH`; имя приводится к виду владельца (без переводов строк, до 64 символов — `normalizePeerName`),
   включение заблокированного владельцем клиента не отправляется; пиры, которых нет локально,
   удаляются (`DELETE`); локальные клиенты, пропавшие у владельца, сбрасываются в `pending:` и будут созданы заново.
4. 401/403 → панель `revoked`, её ноды `uninstalled`.

Всё, что приходит от панели владельца (адрес, порт, ключ и параметры ноды, IP и PSK клиента), проверяется по формату до записи
(`sanitizeRemoteNode`/`sanitizeRemotePeer`, [security.md](security.md)). Нода с некорректными данными получает `uninstalled` и
`last_error`, ошибка попадает в `remote_panels.last_error`; клиент с некорректным IP остаётся `pending:`.

Переименование пользователя или клиента на ноде партнёра запускает синхронизацию сразу (ответ уходит после неё), а не ждёт фонового
цикла раз в минуту. Роуты получателя ждут синхронизацию, когда создают клиентов на нодах партнёра (создание пользователя, клиента), чтобы
в ответе уже были IP и рабочая подписка. Клиенты на ноде партнёра до выдачи IP имеют адрес `pending:<uuid>`
и не попадают в подписку и QR.

## Отключение

- Владелец: отключить доступ (клиенты снимаются с нод), отозвать ноды, удалить доступ (клиенты удаляются каскадом),
  перевыпустить токен.
- Получатель: «Отключить панель» — удаляет своих клиентов у владельца (по возможности) и локально (каскад через
  `remote_panels`). Отдельную ноду партнёра удалить нельзя.
